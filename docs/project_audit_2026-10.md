# Аудит проекта — 2026-10-21

## Общая оценка

Для внутреннего сервиса отдела примерно на 15 пользователей текущая архитектура остаётся рациональной: Django-monolith, PostgreSQL, Nginx/Gunicorn, Docker Compose и Raspberry Pi 5. Переход к микросервисам сейчас не даст практической пользы.

Сильные стороны проекта:

- понятный workflow задачи;
- server-side проверки ролей;
- история изменений;
- уведомления;
- календарь и загрузка сотрудников;
- CI/CD и production deployment;
- backup PostgreSQL и media;
- тесты ключевых сценариев;
- документация по эксплуатации.

## Выполненный рефакторинг

1. Удалён промежуточный `manager_views.py`.
   Проверки владельца задачи теперь находятся непосредственно в `views.py` и используют `can_manage_task` из `permissions.py`.

2. Добавлен `_task_detail_context`.
   Права и формы страницы задачи формируются в одном месте, поэтому GET и ошибочные POST больше не должны расходиться по контексту.

3. Добавлен `_manager_owned_queryset`.
   Очередь проверки и manager-dashboard используют единое правило: обычный Manager проверяет только свои задачи, superuser видит все.

4. UI-геометрия вынесена в `static/css/layout.css`.
   Это отделяет ширину и responsive-layout от бизнес-специфичных стилей `task_review.css`.

5. Удалены старые неиспользуемые стили кастомного login dropdown и общий CSS-патч таблиц, который затрагивал все таблицы проекта.

6. Удалены временные файлы старых patch-итераций.

## Что стоит рефакторить позже

### 1. `signals.py`

`task_notifications_and_history` уже выполняет много обязанностей: история, уведомления, реакции на статусы, сроки и исполнителя. Пока это работает, но следующий безопасный шаг — разделить его на небольшие функции/сервисы по событиям (`status_changed`, `assignee_changed`, `due_date_changed`).

### 2. Явный ответственный Manager

Рекомендация выполнена в v0.7.0: добавлено отдельное поле `Task.responsible_manager`, а `Task.created_by` оставлено неизменяемым автором для аудита. Ответственность теперь можно передавать между руководителями.

### 3. Запросы dashboard/analytics

При росте числа задач стоит проверить количество SQL-запросов через Django Debug Toolbar локально и при необходимости добавить индексы/агрегации. Для текущего масштаба это не блокер.

## Рекомендуемые следующие функции

1. **Ответственный Manager + передача задачи между руководителями.** Самое логичное продолжение текущей модели прав.
2. **Массовые операции.** Выбрать несколько задач и изменить исполнителя, срок, приоритет или менеджера.
3. **Повторяющиеся задачи.** Еженедельные/ежемесячные регламентные работы на основе шаблонов.
4. **Сохранённые представления/фильтры.** Например «мои просроченные», «на этой неделе», «задачи Ирины».
5. **Поиск по всему сервису.** Номер задачи, название, описание, комментарии, сотрудник.
6. **Экспорт отчёта в XLSX/CSV.** Выполненные задачи, просрочки, доработки, фактический цикл по сотрудникам.
7. **Уведомление о риске срока.** Не только «завтра/просрочено», а предупреждение руководителю, если задача ещё `Новая` или не начата близко к сроку.
8. **Архивирование старых задач.** Убирать завершённые задачи старше заданного периода из основных экранов без удаления.
9. **Персональные настройки интерфейса.** Компактность, стартовая страница, сохранённая тема и предпочтительный вид задач на пользователя.
10. **Простой operational dashboard.** Последний backup, место на диске, состояние DB/web/notifier и время последнего успешного deploy.
