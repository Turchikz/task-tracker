# Обзор проекта для отдела метрологии — 2026-10-25

## Назначение и текущий охват

Проект — внутренний менеджер задач для команды примерно из 15 пользователей. Django-монолит, PostgreSQL, Docker Compose, Gunicorn и Nginx подходят для такого размера отдела; переход на микросервисы не нужен.

Текущий продукт уже покрывает общий workflow задач: роли руководителя/сотрудника, распределение между несколькими исполнителями, сроки, приоритеты, проверку результата, комментарии и изображения, историю, календарь, загрузку, уведомления, отсутствие сотрудников, поиск, массовые операции, шаблоны и XLSX-отчёты. Также есть чат, идеи, рулетка и хранилище важных файлов.

Это общий менеджер задач отдела; дальнейшие улучшения стоит направлять на удобство командной работы и регулярных процессов.

## Проведённая проверка

- Изучены конфигурация Django, URL-маршруты, модели, формы, права доступа, сервисы, сигналы, management-команды, шаблоны, CSS/JS, Docker-конфигурация, миграции, тесты и эксплуатационная документация.
- На момент первичного обзора `VERSION` содержал `0.9.18`; в этой доработке версия повышена до `0.19.9`, а README и руководство по версиям синхронизированы.
- Синтаксис всех файлов `static/js/*.js`, UI smoke-тест, CSS brace balance и ссылки на static/URL в шаблонах проверены без замечаний.
- Django `check` и `makemigrations --check --dry-run` прошли. Полный pytest после текущих изменений: 156 passed, 7 failed; сохранились семь ранее наблюдавшихся падений в проверках уведомлений, старых URL проверки, UI assertions и регионального календаря. Новые тесты меток и сроков прошли.
- Проверки запускались на Python 3.14 во временном окружении; production image проекта использует Python 3.13. Docker Desktop недоступен.
- В рабочей папке нет Git-метаданных, поэтому состояние изменений и diff через Git проверить нельзя.
- HTTP-обработчики разделены на task actions/pages, team pages, department pages и reporting; регистрация сигналов отделена от обработчиков событий.

## Оценка архитектуры

### Что уже устроено хорошо

- Django-монолит со связной моделью доступа подходит для 13–15 сотрудников.
- Основные права проверяются на сервере; доступ к задачам строится через общий queryset пользователя.
- Автор задачи отделён от ответственного руководителя, а передача исполнителя сохраняет историю.
- Есть миграции, тесты, CI/CD, резервное копирование базы и пользовательских файлов, отдельный health endpoint и документация эксплуатации.
- Интерфейс уже имеет адаптивные страницы, календарный список для мобильных устройств, доску, сохранённые фильтры и настройки темы.

### Что стоит улучшить в ближайшем цикле

1. **Дальше разделять доменную логику.** HTTP views разложены по модулям, регистрация сигналов отделена от обработчиков. Следующие кандидаты — модели по областям ответственности; делать это небольшими шагами с проверкой миграций.
2. **Закрепить выпуск версии единым процессом.** README и документация используют версию из `VERSION`; changelog и release notes нужно обновлять в одном release checklist.
3. **Продолжить чистку frontend.** Единая cache-busting метка из `VERSION` применяется к локальным CSS/JS, а основные рабочие страницы уже вынесены в верхнюю навигацию. Следующий шаг — загружать ресурсы конкретных разделов только на нужных страницах и проверять макеты в браузере на мобильной и настольной ширине.
4. **Закрепить проверки в воспроизводимой среде.** В рабочей среде проекта обеспечить доступность Django/pytest или Docker Compose, чтобы до релиза запускать system check, `makemigrations --check` и pytest. В полном наборе остаются семь падений, которые нужно классифицировать, прежде чем считать suite зелёным.

## Улучшения менеджера задач для отдела

Предлагаемые изменения касаются организации работы команды:

### Ближайшие улучшения

- Чек-листы в шаблонах для типовых процедур, чтобы согласованные шаги не терялись между исполнителями.
- Дополнить быстрые представления счётчиками задач и напоминаниями о приближении срока; «Скоро срок», «Просрочено» и «Ожидает проверки» уже доступны в списке.
- Проектные метки задач, создаваемые руководителем по мере ввода; метки уже доступны для выбора и фильтрации.
- Более заметные ссылки и вложения к задаче: рабочие инструкции, формы и итоговые документы.

### Следующий этап

- Фиксация причины возврата, результата и выполненных действий в карточке задачи, если это нужно процессу отдела.
- Сводные отчёты по направлениям, просрочкам, повторным доработкам, срокам выполнения и нагрузке сотрудников.
- Архивирование завершённых задач и поиск по архиву без перегрузки основного списка.
- Импорт/экспорт задач и шаблонов для начальной настройки и подготовки отчётов.

Формулировки категорий, чек-листов и обязательных полей лучше согласовать с сотрудниками отдела, чтобы система поддерживала фактический workflow, а не навязывала новую предметную модель.

## Рекомендуемый порядок

1. Стабилизировать текущую сборку: запустить backend checks и тесты в доступной среде, разобрать известные падения, проверить восстановление backup.
2. Согласовать с сотрудниками типовые процедуры и чек-листы.
3. Улучшить напоминания о сроках и добавить счётчики к быстрым представлениям.
4. Настроить представления и отчёты по текущим задачам отдела.
5. После пилота оценить, каких необязательных полей и отчётов реально не хватает команде.
